# Безопасность и развёртывание

Документ отвечает на два вопроса: что в системе защищено, и как безопасно поднять экземпляр на сервере, где уже работают другие приложения.

Важно понимать контекст: этот экземпляр демонстрационный, для жюри. Демо-режим и встроенные моки включены намеренно. Ниже описано, что из этого следует и как изолировать стенд.

## Что включено намеренно

- `DEMO_MODE=true` открывает переключатель персон: вход под демо-кандидата, работодателя и модератора (`POST /api/v1/demo/login-as`). Это нужно жюри, чтобы пройти сценарии без регистрации.
- Вместе с демо-режимом включаются встроенные моки внешних систем: FSP ID (`/mock/fsp`), API достижений, DaData (`/mock/dadata`), ATS (`/mock/ats`). Мок FSP ID принимает вход с паролем `demo` и известным клиентским секретом.
- Документация API открыта: `/api/v1/openapi.json`, `/api/v1/docs`, `/api/v1/redoc`. Жюри этим пользуется.

Из этого следует главное правило: стенд не должен быть доступен всему интернету. Доступ ограничивается сетью и прокси, а не отключением демо.

## Что исправлено в коде

- **SSRF через вебхуки.** Сервер переписывает адрес публичного origin платформы на внутренний (`FSP_SERVER_BASE`). Обычный вебхук на этот origin теперь отклоняется, кроме адреса встроенного мока ATS (`app/integrations/webhooks.py`, функция `check_url`). Проверка стоит и при создании вебхука, и перед каждой отправкой.
- **Изоляция подпроцессов.** Разбор PDF, NER и исполнение SQL на данных кандидата идут в подпроцессах с пределами по памяти, процессорному времени, размеру файла и числу процессов. Из окружения подпроцесса убраны переменные с секретами (`app/common/subproc.py`, `safe_env`, `child_limits`). Раньше сбой нативной библиотеки PDF оставлял в процессе доступ к базе, ключу LLM и сети.
- **Маскирование ПДн перед LLM.** Длинные номера без контрольной суммы (паспорт, водительское) теперь тоже маскируются (`app/llm/masking.py`). Если NER выключен, маскирование считается неполным и текст резюме в LLM не уходит (`app/llm/names.py`, `scan_names`). По умолчанию NER включён.
- **Секрет по умолчанию.** В боевом режиме старт останавливается, если `SECRET_KEY` не задан или остался значением по умолчанию (`app/config/settings.py`, `validate_secrets`). От секрета зависит выбор заданий в тесте.

## Осознанно оставленные риски

- **Запуск прогона лаборатории** (`POST /api/v1/lab/runs`) доступен любому вошедшему пользователю и нагружает процессор на минуты (`app/lab/router.py`). Одновременно идёт только один прогон, зависшие снимаются. На демо это допустимо; на открытом инстансе ограничьте ролью или доступом на уровне прокси.
- **Нет троттлинга входа и регистрации.** Возможен перебор пароля и рассылка писем через регистрацию (`app/auth/router.py`). Для демо, закрытого прокси, риск низкий; для открытого инстанса добавьте лимиты на уровне прокси или в приложении.
- **Прогон теста не прерывается за уход со вкладки.** Это принцип продукта: сигналы честности сохраняются, но не наказывают. Модель угроз описана на странице «Модель угроз».
- **DNS-проверка вебхука и подключение идут разными резолвами** (теоретический DNS rebinding). Смягчено тем, что вебхуки не могут указывать на сам сервис и во внутренние адреса, а редиректы запрещены.

## Чек-лист безопасного развёртывания рядом с другими приложениями

1. **Порты.** Запускать стек с оверлеем `deploy/docker-compose.shared.yml`: наружу открыт только `127.0.0.1:APP_PORT`, порты 80 и 443 не занимаются. Проверить: `ss -ltnp | grep 8080` показывает 127.0.0.1.
2. **Прокси хоста.** Направить домен на `http://127.0.0.1:APP_PORT`. Заголовки безопасности (HSTS, X-Content-Type-Options, X-Frame-Options, Referrer-Policy) выставить на прокси. Пример nginx есть в `deploy/README.md`.
3. **Доступ.** Ограничить стенд: базовый HTTP-аутентификация на прокси, allowlist IP жюри или VPN. Демо отдаёт вход модератором всем, кто дошёл до сервиса.
4. **Секреты.** `SECRET_KEY`, `POSTGRES_PASSWORD` и ключ LLM держать только в `.env` с правами 600. В боевом режиме старт с секретом по умолчанию не пройдёт.
5. **Cookie.** `COOKIE_SECURE=true` и публичный адрес по HTTPS. Без этого cookie сессии уйдёт в открытом виде.
6. **Сеть контейнеров.** Стек живёт в своей сети `fsp2026-shared`. Если нужно запретить контейнерам ходить на другие порты хоста, ограничьте исходящие соединения средствами Докера или firewall.
7. **База.** Порт PostgreSQL наружу не публикуется, доступ только из сети стека. Пароль БД генерируется `bootstrap.sh`.
8. **Обновление.** `git pull` и повторный запуск `up -d --build --wait`. Данные в томе сохраняются, схема обновляется миграциями при старте.
9. **Резервная копия.** `docker compose exec -T db pg_dump -U fsp fsp | gzip > backup-$(date +%F).sql.gz`.

## Что уже сделано хорошо

- Контейнеры без root, без docker.sock, без привилегированных режимов; лимиты памяти и healthcheck на каждом сервисе.
- Сессии: httpOnly-cookie, `SameSite=Lax`, токен хранится хешем, есть срок жизни и отзыв. Пароли через argon2.
- CSRF: обязательный заголовок на изменяющих запросах плюс `SameSite`. Есть проверки владения объектом на всех межаккаунтных чтениях и записях.
- Токены подтверждения, восстановления и согласия опекуна: 256 бит, хранятся хешем, одноразовые, с ограниченным сроком.
- Секреты не пишутся в журналы. События аудита фиксируют просмотр контактов и переключение персон.
