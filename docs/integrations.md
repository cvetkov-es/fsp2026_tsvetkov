# Интеграции

Внешние системы подключены через одну точку и по умолчанию заменены встроенными моками. Переключение на реальную систему делается переменными окружения, код при этом не меняется.

## FSP ID и достижения ФСП

Вход идёт по email с подтверждением или через FSP ID. FSP ID работает по OIDC с PKCE: discovery, обмен кода на токены, проверка ID-токена по JWKS. Профиль кандидата связывается с ID участника по паре `iss+sub`, после чего достижения подтягиваются в профиль. Если FSP ID привязан, кулдауны считаются по нему.

По умолчанию используется встроенный мок по адресу `{PUBLIC_BASE_URL}/mock/fsp`. Переход на настоящий Keycloak ФСП делается только этими переменными:

- `FSP_ID_ISSUER` — issuer реального FSP ID;
- `FSP_ID_CLIENT_ID`, `FSP_ID_CLIENT_SECRET` — клиент;
- `FSP_API_URL` — API достижений;
- `MOCKS_ENABLED=false` — выключить моки.

Статусы привязки:

- `NOT_LINKED` — нейтрально;
- `LINKED_EMPTY`;
- `SYNC_STALE` — используется последний снимок с датой;
- `CONSENT_REVOKED` — данные скрыты, f = 0.

Отображение: уровни результатов по таблице очков ФСП; онлайн-отборы одной строкой; разряды со сроком действия; командные результаты в формате «в составе команды X (3 чел., 2 место из 20)».

Один FSP ID нельзя привязать к двум аккаунтам: ограничение на пару «issuer и subject» держится в базе. Если истории ФСП у кандидата нет, профиль и объяснение дают нейтральную формулировку: «Истории ФСП нет — оценка навыков по тесту». Без минуса и без «0».

## Регистрация и профиль компании

Профиль компании: описание, направление деятельности, контакты. Уровень доверия даёт компании квоты, потребности и дополнительные возможности.

| Уровень | Как получить | Квота приглашений | Активных потребностей | Что ещё даёт |
|---|---|---|---|---|
| L0 | Почта | `QUOTA_L0` | `NEEDS_L0` | Плашка «не проверена» |
| L1 | Корпоративный домен | `QUOTA_L1` | `NEEDS_L1` | Публикация задач, вес голоса `VOTE_W_L1` |
| L2 | Юрлицо через DaData (мок) | `QUOTA_L2` | `NEEDS_L2` | Вес голоса `VOTE_W_L2`, голоса открывают тест выше, помощник к собеседованию |
| L3 | Модератор | как L2 | как L2 | Отметка «проверено» |

## DaData

Проверка юрлица по ИНН для уровня доверия L2. По умолчанию мок возвращает компанию для любого корректного ИНН. Реальный адрес и токен задаются переменными `DADATA_URL` и `DADATA_TOKEN`.

## ATS компании

Работодатель может получать события по приглашениям и этапам найма на свой адрес. Доставка идёт через outbox: событие пишется в той же транзакции, что и действие, а worker доставляет его с повторами.

- Формат: Standard Webhooks. Заголовки `webhook-id`, `webhook-timestamp`, `webhook-signature`, подпись HMAC-SHA256 по строке «id, timestamp, тело».
- Повторы по расписанию, после исчерпания попыток доставка помечается как неуспешная.
- Защита от SSRF: только https и публичный адрес, проверка при создании и перед каждой отправкой, редиректы не выполняются.
- В событии только псевдоним кандидата и ссылки, без ФИО и контактов.
- Для демонстрации есть встроенный мок ATS со страницей принятых событий.

Пример проверки подписи на стороне получателя:

```python
import base64, hashlib, hmac

def verify(secret: str, msg_id: str, timestamp: str, body: str, signature: str) -> bool:
    key = base64.b64decode(secret.removeprefix("whsec_"))
    expected = "v1," + base64.b64encode(
        hmac.new(key, f"{msg_id}.{timestamp}.{body}".encode(), hashlib.sha256).digest()
    ).decode()
    return any(hmac.compare_digest(expected, part) for part in signature.split())
```

## Почта

Письма отправляет worker: подтверждение почты, напоминания, ссылка согласия законного представителя. Для демо используется Mailpit. Без заданного `MAIL_HOST` письма только пишутся в журнал, что удобно локально.

## Параметры

| Имя | Значение |
|---|---|
| `WEBHOOK_MAX_ATTEMPTS` | 5 попыток |
| `WEBHOOK_BACKOFF` | повтор через 1, 5, 30, 120 минут |
| `WEBHOOK_TIMEOUT` | 5 с |
| `WEBHOOK_BATCH` | 50 событий и 20 с за тик |
| `WEBHOOK_ENDPOINTS_MAX` | 5 вебхуков на компанию |
