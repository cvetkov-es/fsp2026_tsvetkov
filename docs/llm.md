# Языковая модель

Модель подключается через OpenAI-совместимый API (по умолчанию провайдер Polza.ai, переменная `LLM_BASE_URL`). Ключ задаётся в `LLM_API_KEY`. Без ключа продукт продолжает работать. Вызов идёт только через модуль `llm`: маскирование → вызов → валидация Pydantic → один повтор → фолбэк.

## Где используется

- **Разбор резюме.** PDF превращается в черновик профиля: стек, опыт, формат, город. Кандидат проверяет и подтверждает.
- **Разбор текста потребности.** Свободный текст вакансии превращается в структуру: специализация, грейды, стек, вилка.
- **Перефразирование объяснений.** Строки объяснения в подборке звучат естественно. Числа и технологии сверяются с фактами карточки, выдуманное отбрасывается.
- **Подсказка к решению задачи.** Работодатель получает совет по ответу кандидата. Решение остаётся за ним.
- **Лаборатория.** Офлайн-проверка ключей банка двумя моделями и судья подбора на синтетике.

Синхронные вызовы — там, где человек ждёт ответа: разбор текста потребности, разбор резюме, сводка при раскрытии карточки. Фоновых вызовов в пути пользователя нет.

## Конвейер разбора резюме

1. pdfplumber / pypdfium2;
2. маскирование (регулярки + Natasha);
3. LLM;
4. черновик, который кандидат подтверждает.

Без LLM основной путь — форма с предзаполнением по словарю стека. Стандартизированный PDF-профиль генерируется автоматически. Если NER выключен или не отработал, текст резюме в модель не отправляется.

## Где работает без модели

Во всех сценариях есть запасной путь: разбор резюме и потребности по правилам и словарю, объяснения по шаблону, вердикты по вычисляемому ключу. Модель улучшает форму, но не держит логику.

## Маршруты и данные

Режим задаётся `LLM_PROFILE`:

- **dev** — только синтетика, данные кандидата не используются;
- **prod** — развёрнутый стенд, где может быть настоящее резюме; тогда данные кандидата идут только к моделям с размещением в России (GigaChat, запасной вариант YandexGPT).

Модель выбирается отдельно под задачу. При старте конфигурация проверяется: если в prod для данных кандидата назначена иностранная модель, старт останавливается. Судья валидации подбора не совпадает с моделью перефразирования.

| Параметр | Значение | Задача |
|---|---|---|
| `LLM_MODEL_PD` | dev: `deepseek/deepseek-v4.1-flash`; prod: `sber/gigachat-2-pro` | разбор резюме и всё, где есть данные кандидата (после маскирования) |
| `LLM_MODEL_PD_FALLBACK` | prod: `yandex/yandexgpt-5.1-pro` | запасная модель для данных кандидата |
| `LLM_MODEL_RUNTIME` | dev: `deepseek/deepseek-v4.1-flash`; prod: `sber/gigachat-2-pro` | разбор потребности, перефразирование объяснений |
| `LLM_MODEL_SOLVER_A` / `_B` | `deepseek/deepseek-v4.1-flash` / `google/gemini-3.8-flash` | офлайн-проверка ключей банка двумя моделями разных семейств, без ПДн |
| `LLM_MODEL_JUDGE` | `google/gemini-3.8-flash` | LLM-судья в валидации подбора на синтетике |
| `LLM_MODEL_AI_POLICY` | `deepseek/deepseek-v4.1-flash` | политика «только ИИ» в лаборатории навыка «Работа с ИИ» |

## Формат ответа

`LLM_JSON_MODE` — таблица `JSON_MODES` в `app/llm/config.py`: для каждой модели свой режим. DeepSeek V4.1 Flash — строгий `json_schema`. GigaChat через агрегатор поддерживает только `json_object`, JSON приходит в markdown-обёртке; в этом режиме модель получает образец объекта, а единственная обёртка разворачивается. Модуль `llm` извлекает первый JSON-объект из ответа, валидирует его через Pydantic и делает один повтор. Извлечение и валидация работают в обоих режимах.

## Надёжность

- **Маскирование.** Персональные данные (почта, телефон, ссылки, ник, дата рождения, длинные номера, ФИО) заменяются метками до отправки. Если маскирование неполное, текст в модель не уходит.
- **Один повтор.** Ответ модели валидируется по схеме, при ошибке делается один повтор, затем включается фолбэк.
- **Circuit breaker.** После `LLM_CB_ERRORS` ошибок вызовы на время прекращаются (`LLM_CB_COOLDOWN_MIN` минут), сценарий уходит на запасной путь.
- **Таймауты.** Обычный вызов — `LLM_TIMEOUT_S`, разбор резюме — `LLM_TIMEOUT_PD_S`, офлайн-задачи лаборатории — `LLM_TIMEOUT_OFFLINE_S`.
- **Проверка фактов.** Каждое число и навык в тексте должны присутствовать во входном JSON.
- **Без фоновых вызовов.** Модель вызывается только там, где человек ждёт ответа.

## Параметры

| Имя | Значение |
|---|---|
| `LLM_PROFILE` | `dev` — разработка, только синтетика, ПДн нет; `prod` — развёрнутый стенд, где жюри может загрузить настоящее резюме |
| `LLM_TIMEOUT_S` | 8 |
| `LLM_CB_ERRORS` / `LLM_CB_COOLDOWN_MIN` | 3 / 10 |
| `LLM_TIMEOUT_PD_S` | 25 — разбор резюме (пользователь ждёт загрузку, ответ длинный; DeepSeek отвечает 5–8 с) |
| `LLM_TIMEOUT_OFFLINE_S` | 60 — офлайн-задачи лаборатории (решатель банка, судья подбора); в интерфейсе их никто не ждёт |
| `LLM_MAX_INPUT_CHARS` | 12 000 символов текста резюме или вакансии на вход LLM |
| `SUMMARY_MAX_CHARS` | 400 — длина перефразированной сводки |
| `LLM_JSON_MODE` | таблица `JSON_MODES` в `app/llm/config.py` |

Стоимость прогонов лаборатории: офлайн-задачи считаются по ключу, обычный прогон на странице лаборатории идёт без обращения к модели.
